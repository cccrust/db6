# v4.11 - Msgq 模組深度重構與 Tokio 效能優化

## 規劃目標

在經歷 v4.10 的轉換陣痛期後，我們發現了 `sync_queue` 與 `async_queue` 在面對 `crate::error::Error` (底層 DB Error) 的轉換不相容挑戰。本版目標將會從**底層 Error mapping** 出發，徹底解決不相容的問題。接著進一步重組 `msgq` 的公用模組，以期最大程度地釋放 **Tokio** 非同步執行時的資源優勢。

### 1. 錯誤處理 (Error Handling) 的相容修復
* **問題點**：v4.10 原有的 `.map_err(MsgqError::Db)` 需要傳入 String 但實際取得的是 `crate::error::Error`。
* **解法**：在 `msgq/error.rs` 補上自動特徵轉換 `impl From<crate::error::Error> for MsgqError`，使得在所有包含 `StorageEngine` 核心調用的地方可以直接使用 `?`。

### 2. 萃取共用儲存邏輯 (Storage Core Extractor)
* `sync_queue`/`sync_pubsub` 與 `async_queue`/`async_pubsub` 其實都是針對同一顆 `BTree / LSM Engine` 在作增刪改查。
* **解法**：針對 `table` 與 `key` (如：`queue:q1:msg1`) 的命名空間規範、序列化等封裝為公用獨立邏輯，讓不同版本直接套用共用模組 (如：`msgq/common/storage.rs`) 來統一資料的落盤行為。

### 3. 全面引入 Tokio 同步原語與 Task 處理
大型 `async_queue.rs` 和 `async_pubsub.rs` 需要依賴更強韌且更輕量的同步設計：
* **`tokio::sync::Notify` 與 `Watch`**：捨棄死等 (Polling) `sleep` 的設計，改由背景線程處理：當訊息 `enqueue` 落盤後，通知正在等待 `dequeue` 的線程。
* **`tokio::sync::mpsc` (Multi-Producer Single-Consumer)**：當進行大量訊息進出隊列時，使用 MPSC 匯集處理以降低檔案系統鎖競爭的問題。
* **Background Worker (`tokio::spawn`)**：自動負責清理到期、過時、死信堆疊。在系統實例化期間與應用程序的生命週期綁定，使用 GracefulShutdown 優雅退場。

### 4. 模組具體拆分 (`async_queue`)
原單一二千行的檔案切割為：
```rust
src/msgq/async_queue/
├── mod.rs        # 模組入口
├── config.rs     # 重試、超期、上限設定
├── metrics.rs    # 健康狀態與分析數據
├── worker.rs     # 背景消費與過期管理 Task
├── facade.rs     # 給對外的 AsyncQueue API
└── ...
```
提供統一乾淨的 `AsyncMsgq` 外觀 (Facade) API！


## 具體執行順序

1. 修復 `src/msgq/error.rs`，加入 `From<crate::error::Error>`。
2. 進行 `sync_queue.rs` 與 `sync_pubsub.rs` 的編譯錯誤掃蕩。
3. 把 `async_queue.rs` 進行瘦身與物理目錄拆分。
4. 在發佈模組中使用 `tokio::sync::Notify` 進行 Publish-Subscriber 的優化。
